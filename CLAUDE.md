# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

MedInv is a self-hosted web app for managing physical media collections (books, CDs, DVDs/Blu-ray) across multiple independent, permission-scoped "libraries". The full requirements/behavior spec is **[`docs/medinv-briefing.md`](docs/medinv-briefing.md)** (German) — it is the source of truth for *what* the app should do; treat it as authoritative over inferring behavior from code alone, and cite its chapter numbers (e.g. "briefing 5.1") in comments/commits when implementing something it specifies. The codebase is an early scaffold built from that spec — it was itself generated with Claude Code against that spec (see README.md's "About this project" / README.de.md's "Über dieses Projekt"), not hand-written; expect it to still read that way. Core CRUD, auth, and permission plumbing are implemented and tested end-to-end; several integration points are intentionally stubbed with `TODO` comments pointing back at the relevant chapter (see "Known-incomplete areas" below) — don't assume a feature is finished just because a controller/service file for it exists.

Stack: Laravel 13 API (`backend/`) + React/TypeScript SPA (`frontend/`), deployed as one Docker image with nginx + php-fpm (`docker/`). Current version: see `backend/config/medinv.php` (single source of truth, exposed at `GET /api/version`).

## Commands

### Backend (`backend/`)
```bash
composer install
touch database/database.sqlite && php artisan migrate   # sqlite is the default MEDINV_DB_CONNECTION
php artisan db:seed              # creates the MEDINV_ADMINUSER/MEDINV_ADMINPASS account (see .env)
php artisan serve                # http://localhost:8000

php artisan test                                   # full suite
php artisan test --filter=TestClassName::test_name # single test
./vendor/bin/pint                                   # fix code style (Laravel/PSR-12); add --test to check without fixing
```

### Frontend (`frontend/`)
```bash
npm install
npm run dev      # http://localhost:5173, talks to backend via VITE_API_BASE_URL (.env)
npx tsc -b       # type-check
npx oxlint       # lint
npm run build    # production build -> dist/
```

### Docker (single image, both apps)
```bash
cd docker
MEDINV_ADMINUSER=admin@example.com MEDINV_ADMINPASS='ChangeMe123!' docker compose up --build
# -> http://localhost:8080 (SPA + same-origin API under /api + /sanctum — no separate API port).
# Override with MEDINV_PortWeb. Add MEDINV_DB_CONNECTION=mariadb|postgres + --profile mariadb|postgres to switch DB backend.
```

## Architecture

### Two apps, one deployable image, one configurable port
`backend/` and `frontend/` are independently run and built (separate `.env`s, separate dev servers) but ship as **one** Docker image (`docker/Dockerfile`): nginx listens on a single port, rendered into `nginx.conf` from `docker/nginx.conf.template` at container start via `envsubst` (`docker/entrypoint.sh`) since nginx can't read env vars directly. `MEDINV_PortWeb` (default 8080) serves the built SPA as static files *and* reverse-proxies `/api/*` + `/sanctum/*` straight to php-fpm, same-origin. This is what every consumer talks to, browser or not — the frontend is built with `VITE_API_BASE_URL=""` for that image so `frontend/src/api/client.ts` calls relative URLs, and same-origin means the deployed app needs no CORS config. There is deliberately no second, dedicated API-only port (an earlier iteration of this project had one, `MEDINV_PortAPI`, and removed it) — keeping a single port with the API strictly confined to the `/api`/`/sanctum` prefixes (`docker/nginx.conf.template`'s `location ^~` blocks) is simpler to reason about and to firewall than two parallel entrypoints into the same backend. The Dockerfile's `HEALTHCHECK` hits Laravel's own `/up` route (`bootstrap/app.php`'s `health: '/up'`) for the same reason `/api`/`/sanctum` need their own explicit `location` blocks: nginx doesn't route anything else to php-fpm by default, so `/up` needs its own exact-match `location = /up` proxy too, or it silently falls through to the SPA's `index.html` and reports "healthy" even with php-fpm completely down.

In local dev, backend and frontend run on two ordinary ports (5173 / 8000 by default, `php artisan serve --port=`), which *does* need CORS + Sanctum's stateful-domain config (see below).

### Auth: Sanctum SPA cookies, not tokens
Login is cookie/session-based (`AuthController`), not bearer tokens. This has a specific, easy-to-get-wrong requirement: a request is only treated as "stateful" (session + CSRF middleware applied) if its `Origin`/`Referer` header matches an entry in `config('sanctum.stateful')` (`backend/config/sanctum.php`, driven by `SANCTUM_STATEFUL_DOMAINS`) — a mismatch (e.g. testing against `127.0.0.1:X` while the domain list says `localhost:X`) fails *silently* as `419`/`500`/session errors, not as a clear auth error. When reproducing auth issues with curl, always send a matching `Origin` header and hit `/sanctum/csrf-cookie` first. `backend/config/cors.php` is a separate, additional requirement for genuinely cross-origin dev (5173 -> 8000) — same-origin production requests don't need it.

**This has bitten real users, not just tests**: a fresh `docker compose up` deployment failed to log in with correct credentials and showed a generic "invalid credentials" message, root-caused to two compounding issues (both now fixed, but the failure mode is worth knowing): (1) `APP_KEY` wasn't set, which throws `MissingAppKeyException` on every request touching cookies — `docker/entrypoint.sh` now auto-generates and persists one in the `storage` volume on first boot, so this shouldn't recur; (2) the accepted login origins didn't cover both hostnames a browser might actually use. `docker/entrypoint.sh` now computes `SANCTUM_STATEFUL_DOMAINS` itself (unless set explicitly) as `localhost:$MEDINV_PortWeb`, `127.0.0.1:$MEDINV_PortWeb`, plus the host parsed out of `MEDINV_URL` if that's set (the public URL a real deployment behind a reverse proxy/domain is reachable at — also used as `APP_URL`). If login ever silently fails again in Docker, check `storage/logs/laravel.log` inside the container before assuming it's a credentials problem — `AuthController`'s `invalid_credentials` error_code is only returned for an actual wrong password/locked/deactivated account; anything else (a 500, a network error) surfaces client-side as the generic `errors.generic` translation instead (see `LoginPage.tsx`) specifically so it's *not* confused with a credentials error again.

### Domain-organized backend, not the Laravel default
Business logic lives in `backend/app/Domain/<Area>/` (Libraries, Metadata, Capture, Backup, ExportImport, Search, Statistics, Security, Mail), one namespace per functional module from briefing chapter 10 ("maximale Modularität"), each injected into thin controllers under `app/Http/Controllers/Api/`. When adding a feature, put the logic in a `Domain` service, not the controller.

Two rules are centralized and must stay that way — every write path routes through them rather than re-implementing the check:
- **Library visibility/write access** (briefing 4.2–4.3: guest/user/admin levels × per-library shares) — `App\Domain\Libraries\LibraryAccessService`. `SearchService` and `StatisticsService` both scope their queries through its `visibleLibrariesQuery()` so an unshared library is invisible there too, per the spec.
- **Per-library duplicate-EAN rejection** (briefing 5.1: same EAN allowed across libraries, forbidden twice in one) — `App\Domain\Libraries\MediaItemService::create()`, used by manual entry, bulk capture, metadata import, and backup/export restore alike.

A media item genuinely captured without a real, known EAN (GitHub issue #151, explicit user request) still needs a value for the `ean` column — every media table's is `NOT NULL` and part of the rule above. `MediaItemService::generateNoEanPlaceholder()` generates a `NoEAN-{13 random digits}` value (19 characters — `database/migrations/*_widen_ean_column_for_no_ean_placeholder.php` widened the column from `varchar(13)`, exactly a real EAN-13/ISBN-13's length, to fit it), regenerating on a per-library collision the same way `create()` itself scopes uniqueness. Reached from two places: `MediaItemController::store()` (the standalone manual-entry form, `ean` now `nullable` in `rulesFor()`) when submitted blank, and `MetadataController::import()` when the confirmed candidate's `attributes.ean` is empty — the latter is what actually makes capturing via free-text metadata search (`MetadataProviderInterface::search()`, previously implemented server-side by every provider but never reachable from the frontend at all) practical: CapturePage.tsx's new "erfassen ohne EAN" search mode feeds a chosen candidate straight into `CreateMediaItemDialog` via its `initialAttributes` prop (reusing `mediaItemFields.ts`'s existing `valuesFromItem()`), and the EAN field there is no longer required. This shipped with a real bug of its own (GitHub issue #155, reported by the user against a live deployment, root-caused via that deployment's own `storage/logs/laravel-*.log`): `disc_count` (`MediaCd`/`MediaDvdBluray`) is a `NOT NULL` column with a DB-level default of 1, but that default only applies when the column is *omitted* from an INSERT/UPDATE, not when it's explicitly `null` — which is exactly what a blank capture-form field (`payloadFromValues()`) or a metadata candidate that doesn't report a disc count (confirmed real for JPC and every LLM-backed provider) always sends, crashing with a `SQLSTATE[23000]` constraint violation instead of the item ever being created. Not specific to the no-EAN flow at all — any manual entry, metadata import/refresh, manual edit, or bulk-update leaving `disc_count` blank hit the same crash. `MediaItemService::withDiscCountDefault()` is the one shared fix, coercing an explicit `null` back to the column's own default of 1, called alongside `withDerivedRuntime()` at every one of those call sites. GitHub issue #156 then asked for the obvious follow-up: a `NoEAN-...` item's own EAN was never a real, scannable code, so `MediaItemDetailDialog`'s "refresh metadata" action can only ever come back `no_match` for one — wasting a real request (real per-call cost, for the LLM providers) per enabled provider for nothing every time it's used. `MediaItemService::isNoEanPlaceholder()` (checking against the same `NO_EAN_PREFIX` constant `generateNoEanPlaceholder()` itself is built from, so the two can't drift apart) is checked in two places: client-side, to grey out the button before the request is even sent, and server-side in `MetadataController::refresh()`, which short-circuits to `no_match` before querying any provider — the actual backstop, since the frontend check alone wouldn't stop a direct API call or a stale page. GitHub issue #166, also reported by the user, found a further gap in this same free-text flow: a chosen candidate's cover, visibly shown in CapturePage.tsx's search-results list, never made it onto the created item — `candidate.cover_urls` sits alongside `attributes`, not inside it (mirroring `MetadataCandidate::toArray()` server-side), so passing only `initialAttributes` into `CreateMediaItemDialog` silently dropped it, and even had it been passed through, that dialog only ever supported a local file upload, never a cover URL, unlike `MetadataController::import()`/`reimport()` (the EAN/merge-review confirm path), which already download a chosen `cover_url` server-side via `CoverDownloadService::download()`. Fixed by giving `MediaItemController::store()` the exact same `cover_url` field and download-after-create behavior (a failed download still leaves the item created, just without a cover, the same tolerance `import()` already has), threading it through as `CreateMediaItemDialog`'s new `initialCoverUrl` prop (previewed, removable, and always superseded by a manually chosen file if one is picked) rather than fetching the image client-side, which a metadata provider's own cross-origin image host generally wouldn't allow from a browser anyway.
- **A media item's cover URL needs a cache-busting query parameter, everywhere it's rendered** (GitHub issue #171, user-reported) — every `<img>` showing a stored cover (full-size or the small generated `/cover/thumbnail`) is keyed off the item's stable `id`, e.g. `.../items/{id}/cover`, which never changes even when the cover itself does (a metadata refresh, GitHub issue #56/#74, replacing it via `MetadataController::reimport()`; a manual re-upload; removal). With no cache-busting, that URL string is byte-identical before and after — React never touches an unchanged `src` attribute on re-render, so the browser has no reason to ever re-fetch it, and the stale image just sits there until a full page reload forces a fresh `<img>` mount. `mediaItemFields.ts`'s `coverSrc()` is the one shared fix, appending the item's current `cover_path` as a `?v=` query value — a reliable token specifically because `CoverDownloadService::store()` always mints a fresh random filename per stored cover (not just any timestamp like `updated_at`, which would also change, and needlessly bust the cache, on an unrelated field edit that never touched the cover at all). Used everywhere a cover is rendered from an item id: `MediaItemDetailDialog.tsx` (both the inline cover and its fullscreen view — the bug as originally reported), `LibraryDetailPage.tsx`'s list thumbnails, `SearchPage.tsx`'s result thumbnails, and `DashboardPage.tsx`'s random-cover carousels — all five shared the identical latent bug, only the detail dialog's had actually been noticed and reported yet. `CreateMediaItemDialog.tsx` doesn't need this: it creates a brand-new item, so its id (and therefore its cover URL) has never been fetched by the browser before.

- **Export/import strips instance-local personal identifiers** (GitHub issue #148, a privacy-review finding) — `ExportImportService::exportLibraries()` never includes an item's `captured_by_user_id` (GitHub issue #74) in its output, the same treatment `id`/`library_id` already got for being meaningless on another instance, and `insertItems()` additionally strips it from whatever an imported file actually contains regardless of source — a raw user ID that happens to collide with a real account on the *importing* instance (most commonly ID 1, the seeded admin) would otherwise falsely attribute that account with having captured an item it never touched, visible in `/reports/user-activity`. `shares[].user_email`, by contrast, is a *deliberate* exception to this same principle — see `exportLibraries()`'s own docblock for why it's intentionally not gated behind `$includeUsers` the way `system_settings`/`users`/`metadata_plugins` are. A library's own `owner_email` (GitHub issue #152, triggered by the user asking whether any data was missing from backups entirely) follows that same `shares[].user_email` precedent — previously absent from the export altogether, silently reassigning every restored library to whoever performed the restore/import instead of its real original owner, a genuine loss for a full backup/restore whose whole point is reproducing the exact prior state. `createLibraryFromExport()`'s `resolveLibraryOwner()` resolves it by email against an existing/just-restored account, falling back to the importing user (not a hard failure) when there's no match — the same tolerance `restoreShares()` already shows for a stale share email. `is_sample_library` was found missing the same way in the same audit and fixed alongside it, though currently inconsequential since nothing else in the app reads that flag yet. GitHub issue #153 then explicitly asked for `captured_by_user_id` itself to still be preserved in a *real* backup specifically (not an ordinary export) — reconciled with #148's own reasoning the same way, as `captured_by_email`: present only when `exportLibraries()` is called with `includeUsers: true`. Two bugs surfaced in the first version of that fix, both reported by the user and both fixed the same day: eager-loading the `capturedBy` relation to read its `->email` leaked a second, redundant `captured_by` key (Eloquent auto-serializes any *loaded* relation unless it's hidden too, same as any attribute) that re-exposed the exact raw id `captured_by_email` exists to avoid — fixed by hiding `capturedBy` explicitly; and resolving `captured_by_email` back onto `captured_by_user_id` on import was originally additionally gated behind `$restoreSettings`, which meant a backup restore that didn't separately opt into "restore settings" (the common case for restoring items/shares without overwriting the current instance's own accounts) silently discarded a perfectly resolvable value — fixed by resolving it unconditionally instead, the same way `owner_email`/`shares[].user_email` themselves already are. `insertItems()`'s own docblock has the full reasoning for both. A raw `captured_by_user_id` a hand-crafted import file might still carry is never trusted regardless. GitHub issue #154, also reported by the user, found the same class of gap one level down: `created_at`/`updated_at` are deliberately absent from every model's `#[Fillable(...)]` list (so an *ordinary* capture/creation path can never be made to spoof either one — a media item's own `created_at` is shown as "Hinzugefügt" in the Recent Additions report), and `exportLibraries()` never included them either, so a restore/import always silently reset both to the current time for every entity it (re-)creates — not just media items, but libraries, users, library shares, saved searches, and metadata plugins alike, everywhere this class recreates a row from scratch. `ExportImportService::applyHistoricalTimestamps()` is the one shared fix for all of them: called explicitly, right after `create()`/`updateOrCreate()`, only from this class's own restore/import call sites — `forceFill()` bypasses mass assignment entirely (letting every *other* caller of e.g. `MediaItemService::create()` stay exactly as unable to spoof a timestamp as before), and `saveQuietly()` avoids firing model events for what is, semantically, still "the original creation" being reproduced, not a genuine update.

`App\Domain\Libraries\CurrencyConversionService` (GitHub issue #64: converts a newly captured item's price into the admin-configured default currency via a live Frankfurter.dev exchange rate) is the deliberate opposite of the two rules above — it's called explicitly from the two genuinely-new-capture controllers (`MediaItemController::store()`, `MetadataController::import()`), not from `MediaItemService::create()` itself, precisely *because* that method is also the backup/import restore path and must reproduce a backup's historical prices exactly rather than re-converting them against today's rate. A future new capture entry point needs to call it explicitly too; it won't happen automatically just by going through `MediaItemService::create()`.

### Three media types, one pattern each
Book/CD/DVD-Blu-ray are three separate tables (`MediaBook`/`MediaCd`/`MediaDvdBluray`) with a fixed, non-overlapping attribute set per briefing chapter 6 — there's no generic "extra field" mechanism by design. A `Library.media_type` is immutable after creation (no update path exists for it anywhere in `LibraryController`). Code that needs to be type-generic (capture, export/import, stats) resolves the right model via `MediaItemService::modelClassFor()` rather than branching on `media_type` ad hoc.

### Metadata plugins are a real interface, not a config flag
`App\Domain\Metadata\Contracts\MetadataProviderInterface` + `MetadataProviderRegistry` (briefing 8.1) is the extension point for new metadata sources — implement the interface under `app/Domain/Metadata/Providers/<MediaType>/`, list the class in `MetadataProviderRegistry::defaultProviders()`, and it becomes toggleable via `metadata_plugins` (admin API) automatically. Books have nine implemented providers (OpenLibrary, Google Books — GitHub issue #20, Hardcover — GitHub issue #18, Amazon — GitHub issue #50, Claude — GitHub issue #59, OpenAI — GitHub issue #65, Gemini — GitHub issue #66, Mistral — GitHub issue #68, JPC — GitHub issue #131); CD has eight (MusicBrainz, Discogs — GitHub issue #22, Amazon, Claude, OpenAI, Gemini, Mistral, JPC — GitHub issue #130); DVD/Blu-ray has eight (UPCMDB, Amazon, Claude, OpenAI, Gemini, Mistral, JPC, TMDB — GitHub issue #157). JPC's book provider (#131) was added after #130's original cd/dvd_bluray-only scoping turned out to be based on a wrong assumption — JPC does sell books — a cautionary example of not trusting an unverified scoping guess over what the user actually knows about a real-world retailer. A fourth scraping provider, Thalia, was implemented (GitHub issue #129) and later removed again (GitHub issue #134) once confirmed permanently non-functional against thalia.de's Cloudflare bot-management — see the `DEFAULT_DISABLED_PROVIDER_KEYS` docblock in `MetadataProviderRegistry` for the full story; it's mentioned here so a future search for "Thalia" in git history isn't mistaken for a still-existing provider. The rest of briefing 8.2's list are `TODO`s in the registry, not missing files to hunt for. The Amazon, Claude, OpenAI, and Gemini providers are all Beta and disabled by default — see "Known-incomplete areas" below. JPC started out the same way but was promoted out of Beta and enabled by default by GitHub issue #145, an explicit user decision after the string of real-world fixes (#133, #135, #136, #138, #140, #143, #144) made it reliable enough for everyday use. `MetadataImportService` only ever calls a provider that has a corresponding, *enabled* `metadata_plugins` row (`MetadataProviderRegistry::enabledProvidersFor()`) — listing a class in `defaultProviders()` alone doesn't activate it. `DatabaseSeeder` calls `syncToDatabase()` (`firstOrCreate`-based, so it's safe to run on every boot) specifically so a fresh install has all default providers enabled from the start; this was in fact missing until GitHub issue #17's investigation surfaced it — before that fix, a truly fresh install had zero enabled providers and every capture/search silently returned "no_match" no matter what was implemented.

A provider with admin-configurable settings (an API key, e.g. `UpcMdbProvider`) also declares `configFields()` (GitHub issue #29) — an array of `MetadataProviderConfigField`s (key/type/required) describing what `metadata_plugins.config` should contain. This is what lets `PluginsPage.tsx` render a real per-plugin settings form instead of a raw JSON textarea, without the frontend needing to know each provider's config shape ahead of time; a provider needing no configuration just returns `[]`. Field labels are deliberately not part of this — like every other backend-defined enum handed to the frontend (e.g. `Library.media_type`), only the stable `key` crosses the API, resolved to a translated label client-side via `admin.pluginConfig.fields.<key>` (falling back to a humanized version of the key for an as-yet-untranslated provider). `metadata_plugins` (including stored config/API keys) rides along on the same `includeUsers`/`restoreSettings` opt-in as user accounts in `ExportImportService` — it's exactly as sensitive as a password hash, so an ordinary library export never includes it, only a real backup does.

Every provider also declares `supportsCodeLookup(): bool` (GitHub issue #158), shown as an "EAN" checkmark column in `PluginsPage.tsx` — same "attach live per request, don't store in the database" shape `version()`/`sourceType()` already established (`MetadataProviderRegistry::eanSupportByProviderKey()`, attached in `MetadataController::plugins()` as `supports_code_lookup`), since this is intrinsic to how the provider is implemented, not admin-configurable state. Declared explicitly rather than inferred from whether `lookupByCode()` happens to return `[]` — an empty result there can just as easily mean "no match for this code", a genuinely different fact. Every provider implemented so far (including the three LLM-backed traits, which genuinely ask the model to look up the given EAN/ISBN/UPC) returns `true`; a proposed TMDB provider (GitHub issue #157, prompted by a feasibility study — TMDB's own `/find/{external_id}` endpoint, confirmed against its live API reference, supports only `imdb_id`/`tvdb_id`/`wikidata_id`/social-media IDs, no barcode of any kind) would be the first real `false`, since it could only ever contribute through `search()`.

### Every MedInv-created table is prefixed `MEDINV_`
Set once via `MEDINV_DB_PREFIX` in `config/database.php` (applied to all four connections: sqlite/mysql/mariadb/pgsql) so the app can share a DB server without collisions (briefing 5.). This is why raw SQL/`DB::table()` calls must not hardcode table names — use Eloquent models or `$this->getTable()`, which already account for the prefix.

### All environment variables are `MEDINV_`-prefixed, including the database ones — with one deliberate exception
Laravel's stock `DB_*` config keys (`DB_CONNECTION`, `DB_HOST`, `DB_PORT`, `DB_DATABASE`, `DB_USERNAME`, `DB_PASSWORD`, `DB_PREFIX`, and the rest) are renamed to `MEDINV_DB_*` throughout `backend/config/database.php` (and the `database`-driver options in `config/cache.php`/`config/queue.php`, which fall back to the same connection) — a deliberate deviation from Laravel's defaults so that *every* variable this project reads from the environment consistently starts with `MEDINV_`, matching the vars from briefing chapter 16. When adding a new Laravel config option that reads `env('DB_...')` by default (e.g. from a fresh `composer require`), rename it the same way rather than leaving a stray unprefixed `DB_*` var. The one intentional exception is plain `TZ` (`SystemSetting::defaultTimezone()`), the near-universal, unprefixed Docker convention for a container's timezone (the same variable Sonarr/Radarr/Immich and most other self-hosted images honor) — treated as a cross-application OS-level standard rather than a MedInv-specific setting, precisely so deployers who already set `TZ` out of habit get the behavior they expect without having to also learn a MedInv-specific variable name. PHP does *not* read `TZ` on its own for `date_default_timezone_get()` (confirmed live — the old automatic fallback no longer exists in modern PHP), and the shipped Alpine image ships no `tzdata` package (no `/etc/localtime`/`/etc/timezone` either), so without this explicit `env('TZ')` read, a deployer's `TZ` setting was silently ignored entirely.

### Environment variables vs. runtime settings — don't confuse the two
Only the handful in briefing chapter 16 (`MEDINV_ADMINUSER`, `MEDINV_ADMINPASS`, `MEDINV_LOGLEVEL`, `MEDINV_TRUSTEDIP`, `MEDINV_RESTOREBACKUP`) plus the database/deployment ones above (`MEDINV_DB_*`, `MEDINV_URL`, `MEDINV_PortWeb`) are env vars, read directly via `env()` (seeder, `BruteForceProtection`, `docker/entrypoint.sh`). Everything else admin-configurable — mail/SMTP, backup interval & retention, brute-force thresholds — lives in the `system_settings` key-value table (`App\Models\SystemSetting::get()/set()`, `AdminSettingsController`) and is meant to be changed at runtime without a restart. `App\Providers\AppServiceProvider::boot()` copies the `mail.*` settings into Laravel's live mail config on every request specifically so `Mail`/`Password::sendResetLink()` pick up the admin-configured SMTP server instead of `.env`'s. The `timezone` runtime setting is a partial exception: once an admin explicitly saves one via `AdminSettingsController::updateTimezone()`, that stored value always wins, but *before* that, its default falls back to the unprefixed `TZ` env var rather than a hardcoded `'UTC'` — see `SystemSetting::defaultTimezone()`'s docblock and the "one deliberate exception" note above.

### API errors carry a machine-readable `error_code`, not just prose
`AuthController::loginError()` returns `{error_code, message}` instead of throwing `ValidationException` — the frontend maps `error_code` to a translated string via `errors.*` i18n keys (`LoginPage.tsx`), rather than pattern-matching on the English `message` text, which would break under a locale change or if the message wording changes. Follow this pattern for any other user-facing API error: add an `error_code`, not just a message, and a matching `errors.<code>` key in both `frontend/src/i18n/locales/{de,en}.json`. Also route it through `Controller::logApiError($request, $errorCode, $message)` (base `App\Http\Controllers\Controller`) so it lands in `storage/logs/laravel.log` with the requesting client's IP alongside the code and message — used today across six controllers (e.g. `AuthController::loginError()`, `UserController::protectedAccountResponse()`, `AdminSettingsController::testMail()`'s failure path), not an exhaustive list — grep for `logApiError(` rather than assuming this paragraph is current.

`errors.generic` is `LoginPage.tsx`'s *own* fallback specifically for an actual failed login attempt with no more specific `error_code` — its wording ("Login failed...") is accurate there and nowhere else. GitHub issue #156 (a follow-up question after #155) found every other unhandled-API-error fallback in the app (`CreateMediaItemDialog.tsx`/`MediaItemDetailDialog.tsx`'s own `describeApiError()`, `adminErrors.ts`'s `describeError()`/`describeBlobError()`, shared across every `admin/*.tsx` page) had been reusing that exact same key/text — so a real 500 while saving a media item read, confusingly, as if the *login* had somehow failed (this is in fact what made #155's own bug report read as an auth issue at first). `errors.actionFailed` is the separate, context-neutral key for all of those; new unhandled-error fallbacks outside LoginPage.tsx should use it, not `errors.generic`.

### Backups live under `storage/app/private/backups`, not `storage/app/backups`
Laravel 11+'s default `local` filesystem disk root is `storage/app/private` (`backend/config/filesystems.php`), not `storage/app` — `BackupService` uses `Storage::disk('local')`, so that's where `.zip` files actually land. Easy to get wrong when adding new storage paths; check `config/filesystems.php` rather than assuming the pre-11 default.

### The DB is update-ready: migrations run automatically, with a safety net
`docker/entrypoint.sh` runs `php artisan migrate --force` on every container start, so a new image with new migration files applies its schema changes with no manual step. Immediately before that, it runs `php artisan medinv:pre-update-backup` (`app/Console/Commands/PreUpdateBackupCommand.php`), which creates a backup via `BackupService` — but only when there are pending migrations *and* the database was already initialized (i.e. this is a real update, not first install or an unchanged restart) — so an update has a restore point without backing up on every ordinary restart. This guarantee depends on `backend/database/` (which holds `migrations/`/`seeders/`/`factories/` — application code, refreshed by every image build) never being covered by a persisted volume itself — only the actual sqlite data file is persisted, at `storage/database/database.sqlite` (nested inside the `storage` volume, not a sibling of the code directories), see the next section and GitHub issue #25 for why this used to be broken.

### The sqlite database file lives under `storage/`, not `backend/database/`
`config/database.php`'s sqlite connection defaults to `database_path('database.sqlite')` (`backend/database/database.sqlite`) for local, non-Docker dev — unchanged, and what the README's `touch database/database.sqlite` step still refers to. Docker deployments are different: `docker/entrypoint.sh` ignores any inherited `MEDINV_DB_DATABASE` for the sqlite case and is authoritative about the path instead, always `storage/database/database.sqlite` — `docker-compose.yml`'s `sqlite-data` named volume mounts onto that nested path (inside the already-persisted `storage` volume) rather than to `backend/database/` directly. Two bugs used to live here (issue #25): `docker-compose.yml` set `MEDINV_DB_DATABASE=medinv` by default — a value only meaningful as a *database name* for mysql/mariadb/postgres — which the sqlite driver silently took as a bogus relative file path, creating the database entirely outside any mounted volume (lost on every container recreation); and even without that, the old fallback path put the database file inside `backend/database/`, the exact directory `sqlite-data` was mounted onto — permanently freezing `migrations/`/`seeders/`/`factories/` at whatever they were when that volume was first created, so no later image update's changes to any of them ever took effect. The `sqlite-data` volume name is deliberately unchanged (only its mount point moved) so an existing deployment's real data keeps working automatically — Compose matches volumes by name, and renaming the key would make Compose treat it as new and empty. `entrypoint.sh` additionally has a defensive one-time move for anyone running the image directly (not via this docker-compose.yml) who had mounted their own volume at the old path.

### Backup restore has two trigger paths, one shared implementation
`BackupService::restore()` (briefing 9.3) reads a backup zip's `manifest.json` back out and hands it to `ExportImportService::importLibraries()` — the same conflict-resolution logic (rename/merge/overwrite/skip/cancel) instance-to-instance import already uses (briefing 9.1), so restore isn't a separate code path. The two triggers differ only in who picks the per-library resolution: `BackupController::restore()` takes `conflict_resolutions`/`restore_settings` from the admin UI request interactively, while `Console\Commands\RestoreBackupOnBoot` (`php artisan medinv:restore-backup <filename>`, run from `docker/entrypoint.sh` whenever `MEDINV_RESTOREBACKUP` is set) has no admin to ask and instead overwrites every conflicting library unconditionally via `importLibraries()`'s `__default__` conflict-resolution sentinel, plus always restores settings and user accounts — `MEDINV_RESTOREBACKUP`'s whole purpose is bringing the instance to exactly the backed-up state, e.g. resetting a demo/staging deployment on every restart.

GitHub issue #167 (user-reported gap) added a third way a `Backup` row comes to exist: `BackupController::upload()`/`BackupService::upload()` accept a backup `.zip` an admin already has locally (downloaded earlier from this or another instance) and store it exactly like a server-generated one — same `backups/` disk location, same `backups` table row (`trigger: 'manual'`, so it's exempt from automatic retention the same way clicking "Jetzt sichern" already is), reachable through the exact same list/download/restore/delete actions from there on. This is deliberately the fuller counterpart to `ExportImportController::import()`'s own file upload, which accepts the identical zip shape (`manifest.json` + `covers/`) but whose frontend (`ExportImportPage.tsx`) never exposes `restore_settings` — so a backup uploaded there could only ever restore library data, never the user accounts/settings/plugins a real backup also carries. `BackupService::upload()`'s own validation stays as light as `restore()` itself already tolerates (must open as a real zip, must contain a `manifest.json` that decodes to a JSON array) — the deeper structural checks (`ExportImportService::assertValidPayload()`) already run naturally the moment the uploaded backup is actually restored, same as any other backup.

That upload feature immediately hit a real-world limit GitHub issue #168 traced live against a running deployment: `php:8.4-fpm-alpine`'s stock `upload_max_filesize`/`post_max_size` (2M/8M) were never overridden anywhere in this project before this fix, and a real backup `.zip` commonly runs 15–20MB+ once a collection has enough cover images — a request over `post_max_size` makes PHP silently drop `$_FILES`/`$_POST` entirely rather than erroring cleanly, which is what surfaced client-side as a confusing 500 (nginx's own `client_max_body_size`, 20m, contributed a straight 413 for the largest files, right at that same ceiling). `docker/uploads.ini` (raising both to 512M, copied into PHP's own `conf.d` scan directory by the Dockerfile — confirmed live via `php -r 'echo PHP_CONFIG_FILE_SCAN_DIR;'` — rather than editing `php.ini` directly) and a matching bump of `nginx.conf.template`'s `client_max_body_size` fix this — not specific to the upload endpoint at all, since both limits apply at the PHP/nginx layer regardless of route, so `POST /admin/import` (briefing 9.1) had silently carried the exact same latent ceiling the whole time. One real gotcha worth remembering here: a first version of `uploads.ini` used `#`-style comments, which broke PHP's ini parser outright (`syntax error, unexpected '('`, confirmed live) and silently left the *entire* file unparsed — `.ini` files reliably only support `;` as a comment character, not `#`.

GitHub issue #169 (a follow-up user report right after #167 shipped) found a cosmetic-but-confusing gap in the upload feature itself: the stored filename's timestamp was always the moment of *upload*, not the original backup's own point in time (`create()`'s naming convention, `medinv-backup-{timestamp}.zip`, doubles as the only place that timestamp is recorded at all — it isn't a manifest field) — so re-uploading a backup downloaded weeks ago made it look like a fresh one. `BackupService::filenameForUpload()` now reuses the original filename's timestamp when it's present, but only when the uploaded file's name fully matches this app's own naming convention via `preg_match` — never trusting the name verbatim otherwise (a renamed file, or one from outside this app entirely, still falls back to the current time exactly as before this fix) — and only after confirming no on-disk collision (re-uploading the exact same file twice, or two originals whose timestamps happen to coincide, appends a numeric suffix rather than silently overwriting the earlier one).

### Automatic backups need both a Laravel schedule entry and something to actually invoke it
`backup.interval_mode`/`backup.cron_expression` (briefing 9.2, admin-configurable via `AdminSettingsController::updateBackup()`) are resolved into an actual cron expression by `BackupService::scheduledBackupCronExpression()`, registered in `routes/console.php` — but that alone isn't enough, since this image has no system cron daemon. `docker/supervisord.conf` runs a third process (`[program:scheduler]`) alongside nginx/php-fpm, a plain shell loop calling `php artisan schedule:run` every 60 seconds — Laravel's own scheduler resolution. The task itself is registered as `->everyMinute()`, not a dynamic `->cron($expression)`: `routes/console.php` loads on *every* console bootstrap (any artisan command, not just `schedule:run`), so evaluating `SystemSetting::get()` at registration time broke `php artisan migrate --force` itself on a brand-new database (no `system_settings` table yet) — the actual due-check happens inside the scheduled closure instead, via `Cron\CronExpression::isDue(Carbon::now())` (the explicit `Carbon::now()` matters too — `isDue()`'s own `'now'` default builds a plain `DateTime`, which ignores `Carbon::setTestNow()` and made this untestable otherwise).

### Fuzzy search is backend-specific, with a portable fallback everywhere else
`SearchService`'s `fuzzy` flag (briefing 13.) resolves differently depending on the active `MEDINV_DB_CONNECTION`, since there's no single privilege-free, index-usable typo-tolerant primitive across sqlite/mariadb/pgsql. On Postgres with the `pg_trgm` extension actually installed, it uses `word_similarity`'s indexable `%>` operator against a GIN trigram index built on `LOWER(column)` (a migration, `database/migrations/*_add_pg_trgm_indexes_for_media_search.php`, iterates `SearchService::SEARCHABLE_COLUMNS` — the single source of truth for searchable columns — to create these; deliberately `word_similarity`/`%>`, not plain `similarity()`/`%`, since the latter scores against a compared string's *entire* length and badly under-scores a short query cleanly matching inside a long field like `description`). Everywhere else (sqlite, mariadb/mysql, or a pgsql connection where `CREATE EXTENSION pg_trgm` failed — self-hosted Postgres instances don't always grant that privilege, and the migration is deliberately non-fatal if it does) falls back to `FuzzyTextMatcher`, a pure PHP word-level Levenshtein matcher: since a typo'd query word has by definition no substring overlap with the correctly-spelled field value, there's no SQL-level `LIKE` pre-filter that could narrow the candidate set without risking excluding the very row that should match, so this path loads every row in the visible libraries (still scoped through `LibraryAccessService`) and matches in PHP — an accepted trade-off given this app's realistic data volumes. `SearchService::pgTrgmAvailable()` checks (cached via the `database` cache store, not an in-process property — `SearchService` isn't a singleton, so per-request state buys nothing) whether the extension actually ended up installed, so a privilege-restricted Postgres deployment gets the same behavior as sqlite/mariadb rather than an error.

- LLM-backed metadata providers (Claude, GitHub issue #59; OpenAI, GitHub issue #65; Gemini, GitHub issue #66; and Mistral, GitHub issue #68 — all four across all three media types) are a fourth provider category alongside the plain-API and scraping ones above — `App\Domain\Metadata\Providers\Claude\ClaudeMetadataProvider` / `App\Domain\Metadata\Providers\OpenAi\OpenAiMetadataProvider` / `App\Domain\Metadata\Providers\Gemini\GeminiMetadataProvider` / `App\Domain\Metadata\Providers\Mistral\MistralMetadataProvider` (each a shared trait) + `{Claude,OpenAi,Gemini,Mistral}{Book,Cd,DvdBluray}Provider` call the Anthropic Messages API / OpenAI Responses API / Google Generative Language `generateContent` API / Mistral's Conversations API directly (raw `Http::`, matching every other provider's zero-SDK convention) with structured outputs and a server-side web-search tool declared on every request, so the model grounds its answer in a real page instead of answering from training knowledge alone. The four vendors' request/response shapes differ in several concrete ways beyond just the endpoint/model (see `OpenAiMetadataProvider`'s, `GeminiMetadataProvider`'s and `MistralMetadataProvider`'s own docblocks for the itemized lists, each verified against that vendor's current API reference before implementing rather than from training knowledge, per the same caution #59's own docblock already documents for Claude) — notably, OpenAI's structured-output schema lives under `text.format` (with a required schema `name`, which neither Claude nor Gemini has an equivalent for) rather than `output_config.format`/`generationConfig.responseSchema`, its `input` array carries the system-role turn inline rather than a separate top-level `system` string/`systemInstruction` object; Gemini's `responseSchema` is a subset of the OpenAPI 3.0 Schema Object rather than plain JSON Schema, so nullability is a sibling `nullable: true` boolean instead of Claude/OpenAI's `type: [T, "null"]` union, and its web-search tool (`{"googleSearch": {}}`) needs an explicit PHP `(object) []` rather than `[]` to json_encode as `{}` instead of `[]`; Mistral needs a genuinely different endpoint entirely (`/v1/conversations`, not `/v1/chat/completions` — see below) with its own `inputs`/`instructions` fields and an `outputs` array of typed entries (a `message.output` entry's `content` is either a plain string or an array of `{text}` chunks) rather than any of the other three vendors' response envelopes; a declined request surfaces as a `"refusal"`-type content item for OpenAI, a top-level `stop_reason` flag for Claude, a prompt-level `promptFeedback.blockReason` (with no `candidates` array at all) for Gemini, and has no documented equivalent at all for Mistral (an absent/textless `message.output` entry is the one generic fallback used there instead). The admin-configurable `prompt` setting is a `'textarea'`-type `MetadataProviderConfigField` (GitHub issue #59's addendum, the first use of that field type) pre-filled with a default naming real retailers/databases (JPC, Thalia, Amazon, Discogs, IMDb, WorldCat) to check — identical wording across all four vendors, since the instruction itself isn't model-specific. `price`/`currency` are deliberately never requested (an even worse hallucination risk than an exact ISBN) and `coverUrls` is always `[]` (a plain chat completion can't return a genuine existing image URL). `sourceType()` returns `'llm'`, a third value alongside `'api'`/`'scraping'` (GitHub issue #55) — like Amazon above, `version()` is `"v0.1-beta"` and all twelve providers (three each for Claude, OpenAI, Gemini, Mistral) are disabled by default; unlike Amazon, none of them was ever live-verified against the real Anthropic/OpenAI/Google/Mistral API (all four network-reachable from this sandbox but no usable credentials — see each trait's own docblock). All four `{Claude,OpenAi,Gemini,Mistral}DvdBlurayProvider::ITEM_FIELDS` carry `genre`/`subtitles` (GitHub issue #140, identical shape/pattern to `cast`) since `MediaDvdBluray` has both columns — an ordinary schema addition, not a confirmed/unconfirmed distinction, since a grounded LLM answer isn't scraped markup with a specific label to (dis)confirm.

  Mistral (GitHub issue #68) is a deliberate exception to how confidently the other three vendors' integrations could be pinned down: the issue's own technical note flagged, up front, that Mistral's web-search tool might need a heavier API than the other vendors' single-request pattern — confirmed true. `web_search`/`web_search_premium` are documented, word for word across two independent official pages, as *not* supported on `/v1/chat/completions` (the endpoint every other vendor's own equivalent uses) — only on `/v1/conversations` or the fuller Agents API. `MistralMetadataProvider` uses `/v1/conversations` directly rather than the heavier Agents API, since `agent_id` is documented as optional there — a single inline request per lookup, the same one-call-per-lookup shape every other LLM provider here uses, just via a different endpoint. One real gap stayed unconfirmed despite extensive research and is explicitly disclosed rather than guessed past (the issue's own explicit instruction): whether `completion_args.response_format` (`completion_args` is documented only as "white-listed arguments from the completion API") actually accepts `json_schema` structured output, and specifically whether that combines with the `web_search` tool in the same request. `MistralMetadataProvider` sends that combination anyway, on the reasoning that a "white-listed" subset of the chat-completions API most plausibly reuses that API's own confirmed `response_format` shape — if Mistral's API actually rejects it, the request fails with a non-2xx status, surfaced as an ordinary per-provider `'failed'` status (GitHub issue #53) exactly like any other genuine request failure, never silently swallowed.
- TMDB (The Movie Database, DVD/Blu-ray only, GitHub issue #157) is a fifth provider category in a sense that matters structurally, not just historically: `App\Domain\Metadata\Providers\DvdBluray\TmdbProvider` is the first provider anywhere in this app whose `supportsCodeLookup()` (GitHub issue #158) is genuinely `false` — confirmed against TMDB's own live API reference for `/find/{external_id}` (only `imdb_id`/`tvdb_id`/`wikidata_id`/social-media IDs, no barcode of any kind) rather than assumed. `lookupByCode()` always returns `[]`; the provider only ever contributes through `search()`, which the existing free-text "ohne EAN erfassen" flow (GitHub issue #151) already calls for every enabled provider — no new integration point was needed to make TMDB usable as soon as a film's title is known, exactly the shape a requested feasibility study recommended over a bigger, separate two-stage pipeline — GitHub issue #159 then asked for that bigger pipeline anyway, implemented as described below. `search()` maps most candidates straight from `GET /search/movie`'s own response fields (title, overview, release_date, poster, and `genre_ids` translated to names via a separately cached `GET /genre/movie/list`), the same "don't fan out into N extra requests per search" discipline every other `search()` implementation here already follows. GitHub issue #165 (a further explicit user request, after asking why cast/director/runtime stayed empty) is a deliberate, bounded exception to that discipline: TMDB's cast/crew and runtime are only available via a per-title `GET /movie/{id}` detail call (`runtime` directly, `credits.cast[]`/`credits.crew[]` — director via `job === "Director"` — through `append_to_response=credits`, field names confirmed live against the official reference), and only the first `MAX_ENRICHED_RESULTS` search results (1, left deliberately conservative rather than a permanent ceiling) get that extra call via `movieDetailsWithCredits()`; every other result stays exactly as unenriched as before. `castFrom()` also caps the mapped cast to `MAX_CAST_MEMBERS` (10), sorted by TMDB's own billing `order` field — a real cast list can run to 50+ credited/uncredited entries, not a usable value for this app's plain free-text `cast` field as-is. This compounds with GitHub issue #159's own second-stage round, which can search up to 3 different titles per single EAN scan (`MAX_TITLE_CANDIDATES`) — up to 3 extra detail requests per scan now that round 2 runs automatically, not just per manual free-text search. Like Amazon/Claude/OpenAI/Gemini/Mistral, `version()` is `"v0.1-beta"` and it's disabled by default (`DEFAULT_DISABLED_PROVIDER_KEYS`) — for a different reason than any of those, though: TMDB's own API Terms of Use prohibit caching API data for longer than six months, a real, unresolved tension with this app's whole purpose of permanent, self-hosted collection storage that the feasibility study flagged as needing an admin's own explicit decision rather than silent enable-by-default. That same study is also why TMDB's required attribution (logo + a specific notice sentence, quoted verbatim from TMDB's API Terms of Use rather than paraphrased) is rendered in `PluginsPage.tsx`'s settings dialog for this one plugin specifically (`frontend/src/assets/tmdb-logo.svg` is TMDB's own official "short" SVG mark from `themoviedb.org/about/logos-attribution`, fetched directly, not redrawn) — the only place in the app an admin actually configures it, and thus the only place an attribution notice would ever be seen. The config field itself is keyed `read_access_token`, not the `api_key` key every other API-key-gated provider shares — a first version reused `api_key` and was corrected after the user pointed out a real risk of confusion: TMDB issues two genuinely different credentials (a short v3 "API Key" and this provider's actual long, JWT-shaped "API Read Access Token"), and the shared `api_key` label would have invited pasting in the wrong one (see `TmdbProvider::configFields()`'s own comment). GitHub issue #160, a further explicit user request, added a "Test" button to that same settings dialog — shown only when a provider implements the new, deliberately optional `App\Domain\Metadata\Contracts\TestableMetadataProvider` (`testConfig(array $config): bool`, exposed per-provider the same "attach live per request" way as `version()`/`sourceType()`/`supportsCodeLookup()`, via `MetadataProviderRegistry::testableByProviderKey()`'s `supports_config_test` attribute) — that checks the *currently typed* config, not necessarily already saved, against the real API before an admin commits to it. `TmdbProvider::testConfig()` uses TMDB's own dedicated `GET /authentication` endpoint, confirmed live to return exactly the `200`-valid/`401`-invalid distinction the user's own request anticipated; every other status (network failure, a 5xx) throws rather than being folded into "invalid", the same "don't conflate 'confirmed wrong' with 'couldn't check'" distinction GitHub issue #53 already established elsewhere for a provider request failure. Deliberately not part of `MetadataProviderInterface` itself and not implemented by most providers — a real per-provider test is meaningful for very different reasons (a wrong key vs. no credential concept at all vs., for the LLM providers, a genuine per-call cost that a "test" spending a real generation request would work against). GitHub issue #170 (a further explicit user request) made every request this provider makes — search, the per-title detail/credits enrichment, and the genre-name list — honor the requesting user's own `preferred_language` rather than always querying in whatever TMDB defaults to. `TMDB_LANGUAGE_BY_CODE` translates this app's own short `preferred_language` codes (e.g. `'de'`) to the full `ISO-639-1-ISO-3166-1` tag TMDB's `language` parameter actually expects (`'de-DE'`) — confirmed against TMDB's `GET /search/movie` reference (defaulting to `"en-US"`) and its `GET /configuration/primary_translations` example response, which lists a specific region for every one of this app's supported languages except Icelandic (not present in that list at all, so `'is-IS'` there is the standard ISO combination, not itself TMDB-confirmed the way the other sixteen are). Read via `Auth::user()?->preferred_language` directly inside the provider rather than threaded through as a new `search()` parameter — `MetadataProviderInterface`'s signature is shared across roughly twenty provider classes and deliberately not widened for one provider's benefit — falling back to `'de'` the same tolerant way `PdfExportService::languageFor()` already does elsewhere in this app, and further falling back to TMDB's own `"en-US"` default for a `preferred_language` with no entry in the map at all. The genre-list cache key (previously a single fixed string, shared — and served stale-language — across every user) now includes the resolved language, since genre names are themselves translated by TMDB and a one-day-cached English response must never leak to a German-preferring user's search just because an English-preferring user happened to search first.

GitHub issue #159 then asked for exactly the bigger two-stage pipeline the feasibility study had deliberately deferred: a provider that can never contribute through `lookupByCode()` at all should still get a real chance during an ordinary EAN scan, not only through manually switching to free-text search. `MetadataImportService::collectCandidatesByCode()` now runs two rounds — the first (EAN) round now actively *skips* calling `lookupByCode()` for a `supportsCodeLookup() === false` provider (previously called anyway for a guaranteed `[]`); a second round then calls `search()` on exactly those skipped providers, still only for providers that structurally have no other way to ever contribute (not every EAN-capable provider that happened to report `no_match` this time, which would multiply request volume — and, for a paid API, cost — across the board rather than just filling the one real gap). A provider with genuinely nothing to search with (round 1 found no candidates at all, or none reported a title) gets a new `skipped` `provider_statuses` entry instead of silently vanishing, the same transparency GitHub issue #53 already established for `failed` vs. `no_match`. The only new, additive piece of information threaded through the response is a `stage` (`'code'` | `'title'`) on each `provider_statuses` entry — `MetadataMergeReview.tsx`'s `ProviderStatusList` (already rendered alongside every merge review in both `CapturePage.tsx` and `MediaItemDetailDialog.tsx`) labels a `stage: 'title'` contribution as "gefunden über Titel", addressing the same feasibility study's own caution that title-based matching is inherently less certain than a barcode-confirmed one. Both `BulkImportService::resolveOne()` and `MetadataController::refresh()` get this for free, since both already call `lookupMerged()`, the one place this is wired in.

The first version of round 2 only ever tried a single title — the one every round-1 candidate agreed on — and skipped round 2 outright the moment EAN-capable providers disagreed with each other, on the reasoning that guessing wrong risked silently mixing in a completely unrelated film's data. The user found that traded away too much: even a disagreement (e.g. a barcode shared by more than one real release — `DiscogsProvider`'s own docblock documents this happening live) usually still has the correct title among the top few most-supported candidates, just not the *only* one reported. `resolveCandidateTitles()` (private, `MetadataImportService`) now always tries up to `MAX_TITLE_CANDIDATES` (3) titles, ranked by how many round-1 providers reported each one — reusing `MetadataMerger`'s own per-field `options` (already grouped/deduped) rather than any new merge logic, so this still required no changes to `MetadataMerger`/`MetadataCandidate`. A single title when every round-1 candidate agrees (unchanged from before), up to three when they don't, instead of an all-or-nothing skip. `queryProvidersByTitles()` (replacing the earlier, now-round-1-only `queryProviders()` for this purpose) tries every title-only provider against each of those titles in turn and collapses the attempts into one `provider_statuses` entry per provider — `'ok'` if *any* attempt found something (aggregate `candidate_count`), `'no_match'` if every attempt cleanly found nothing, `'failed'` only if *every* attempt errored (a mix of one real "nothing here" answer and another attempt's transient error is still reported by the real answer, not swallowed by the error).
