# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

MedInv is a self-hosted web app for managing physical media collections (books, CDs, DVDs/Blu-ray) across multiple independent, permission-scoped "libraries". The full requirements/behavior spec is **[`docs/medinv-briefing.md`](docs/medinv-briefing.md)** (German) — it is the source of truth for *what* the app should do; treat it as authoritative over inferring behavior from code alone, and cite its chapter numbers (e.g. "briefing 5.1") in comments/commits when implementing something it specifies. The codebase is an early scaffold built from that spec — it was itself generated with Claude Code against that spec (see README.md's "About this project" / README.de.md's "Über dieses Projekt"), not hand-written; expect it to still read that way. Core CRUD, auth, and permission plumbing are implemented and tested end-to-end; several integration points are intentionally stubbed with `TODO` comments pointing back at the relevant chapter (see "Known-incomplete areas" below) — don't assume a feature is finished just because a controller/service file for it exists.

Stack: Laravel 13 API (`backend/`) + React/TypeScript SPA (`frontend/`), deployed as one Docker image with nginx + php-fpm (`docker/`). Current version: see `backend/config/medinv.php` (single source of truth, exposed at `GET /api/version`).

## Commands

### Backend (`backend/`)
```bash
composer install
touch database/database.sqlite && php artisan migrate   # sqlite is the default MEDINV_DB_CONNECTION
php artisan db:seed              # creates the MEDINV_ADMINUSER/MEDINV_ADMINPASS account (see .env)
php artisan serve                # http://localhost:8000

php artisan test                                   # full suite
php artisan test --filter=TestClassName::test_name # single test
./vendor/bin/pint                                   # fix code style (Laravel/PSR-12); add --test to check without fixing
```

### Frontend (`frontend/`)
```bash
npm install
npm run dev      # http://localhost:5173, talks to backend via VITE_API_BASE_URL (.env)
npx tsc -b       # type-check
npx oxlint       # lint
npm run build    # production build -> dist/
```

### Docker (single image, both apps)
```bash
cd docker
MEDINV_ADMINUSER=admin@example.com MEDINV_ADMINPASS='ChangeMe123!' docker compose up --build
# -> http://localhost:8080 (SPA + same-origin API under /api + /sanctum — no separate API port).
# Override with MEDINV_PortWeb. Add MEDINV_DB_CONNECTION=mariadb|postgres + --profile mariadb|postgres to switch DB backend.
```

## Architecture

### Two apps, one deployable image, one configurable port
`backend/` and `frontend/` are independently run and built (separate `.env`s, separate dev servers) but ship as **one** Docker image (`docker/Dockerfile`): nginx listens on a single port, rendered into `nginx.conf` from `docker/nginx.conf.template` at container start via `envsubst` (`docker/entrypoint.sh`) since nginx can't read env vars directly. `MEDINV_PortWeb` (default 8080) serves the built SPA as static files *and* reverse-proxies `/api/*` + `/sanctum/*` straight to php-fpm, same-origin. This is what every consumer talks to, browser or not — the frontend is built with `VITE_API_BASE_URL=""` for that image so `frontend/src/api/client.ts` calls relative URLs, and same-origin means the deployed app needs no CORS config. There is deliberately no second, dedicated API-only port (an earlier iteration of this project had one, `MEDINV_PortAPI`, and removed it) — keeping a single port with the API strictly confined to the `/api`/`/sanctum` prefixes (`docker/nginx.conf.template`'s `location ^~` blocks) is simpler to reason about and to firewall than two parallel entrypoints into the same backend. The Dockerfile's `HEALTHCHECK` hits Laravel's own `/up` route (`bootstrap/app.php`'s `health: '/up'`) for the same reason `/api`/`/sanctum` need their own explicit `location` blocks: nginx doesn't route anything else to php-fpm by default, so `/up` needs its own exact-match `location = /up` proxy too, or it silently falls through to the SPA's `index.html` and reports "healthy" even with php-fpm completely down.

In local dev, backend and frontend run on two ordinary ports (5173 / 8000 by default, `php artisan serve --port=`), which *does* need CORS + Sanctum's stateful-domain config (see below).

### Auth: Sanctum SPA cookies, not tokens
Login is cookie/session-based (`AuthController`), not bearer tokens. This has a specific, easy-to-get-wrong requirement: a request is only treated as "stateful" (session + CSRF middleware applied) if its `Origin`/`Referer` header matches an entry in `config('sanctum.stateful')` (`backend/config/sanctum.php`, driven by `SANCTUM_STATEFUL_DOMAINS`) — a mismatch (e.g. testing against `127.0.0.1:X` while the domain list says `localhost:X`) fails *silently* as `419`/`500`/session errors, not as a clear auth error. When reproducing auth issues with curl, always send a matching `Origin` header and hit `/sanctum/csrf-cookie` first. `backend/config/cors.php` is a separate, additional requirement for genuinely cross-origin dev (5173 -> 8000) — same-origin production requests don't need it.

**This has bitten real users, not just tests**: a fresh `docker compose up` deployment failed to log in with correct credentials and showed a generic "invalid credentials" message, root-caused to two compounding issues (both now fixed, but the failure mode is worth knowing): (1) `APP_KEY` wasn't set, which throws `MissingAppKeyException` on every request touching cookies — `docker/entrypoint.sh` now auto-generates and persists one in the `storage` volume on first boot, so this shouldn't recur; (2) the accepted login origins didn't cover both hostnames a browser might actually use. `docker/entrypoint.sh` now computes `SANCTUM_STATEFUL_DOMAINS` itself (unless set explicitly) as `localhost:$MEDINV_PortWeb`, `127.0.0.1:$MEDINV_PortWeb`, plus the host parsed out of `MEDINV_URL` if that's set (the public URL a real deployment behind a reverse proxy/domain is reachable at — also used as `APP_URL`). If login ever silently fails again in Docker, check `storage/logs/laravel.log` inside the container before assuming it's a credentials problem — `AuthController`'s `invalid_credentials` error_code is only returned for an actual wrong password/locked/deactivated account; anything else (a 500, a network error) surfaces client-side as the generic `errors.generic` translation instead (see `LoginPage.tsx`) specifically so it's *not* confused with a credentials error again.

### Domain-organized backend, not the Laravel default
Business logic lives in `backend/app/Domain/<Area>/` (Libraries, Metadata, Capture, Backup, ExportImport, Search, Statistics, Security, Mail), one namespace per functional module from briefing chapter 10 ("maximale Modularität"), each injected into thin controllers under `app/Http/Controllers/Api/`. When adding a feature, put the logic in a `Domain` service, not the controller.

Two rules are centralized and must stay that way — every write path routes through them rather than re-implementing the check:
- **Library visibility/write access** (briefing 4.2–4.3: guest/user/admin levels × per-library shares) — `App\Domain\Libraries\LibraryAccessService`. `SearchService` and `StatisticsService` both scope their queries through its `visibleLibrariesQuery()` so an unshared library is invisible there too, per the spec.
- **Per-library duplicate-EAN rejection** (briefing 5.1: same EAN allowed across libraries, forbidden twice in one) — `App\Domain\Libraries\MediaItemService::create()`, used by manual entry, bulk capture, metadata import, and backup/export restore alike.

A media item genuinely captured without a real, known EAN (GitHub issue #151, explicit user request) still needs a value for the `ean` column — every media table's is `NOT NULL` and part of the rule above. `MediaItemService::generateNoEanPlaceholder()` generates a `NoEAN-{13 random digits}` value (19 characters — `database/migrations/*_widen_ean_column_for_no_ean_placeholder.php` widened the column from `varchar(13)`, exactly a real EAN-13/ISBN-13's length, to fit it), regenerating on a per-library collision the same way `create()` itself scopes uniqueness. Reached from two places: `MediaItemController::store()` (the standalone manual-entry form, `ean` now `nullable` in `rulesFor()`) when submitted blank, and `MetadataController::import()` when the confirmed candidate's `attributes.ean` is empty — the latter is what actually makes capturing via free-text metadata search (`MetadataProviderInterface::search()`, previously implemented server-side by every provider but never reachable from the frontend at all) practical: CapturePage.tsx's new "erfassen ohne EAN" search mode feeds a chosen candidate straight into `CreateMediaItemDialog` via its `initialAttributes` prop (reusing `mediaItemFields.ts`'s existing `valuesFromItem()`), and the EAN field there is no longer required. This shipped with a real bug of its own (GitHub issue #155, reported by the user against a live deployment, root-caused via that deployment's own `storage/logs/laravel-*.log`): `disc_count` (`MediaCd`/`MediaDvdBluray`) is a `NOT NULL` column with a DB-level default of 1, but that default only applies when the column is *omitted* from an INSERT/UPDATE, not when it's explicitly `null` — which is exactly what a blank capture-form field (`payloadFromValues()`) or a metadata candidate that doesn't report a disc count (confirmed real for JPC and every LLM-backed provider) always sends, crashing with a `SQLSTATE[23000]` constraint violation instead of the item ever being created. Not specific to the no-EAN flow at all — any manual entry, metadata import/refresh, manual edit, or bulk-update leaving `disc_count` blank hit the same crash. `MediaItemService::withDiscCountDefault()` is the one shared fix, coercing an explicit `null` back to the column's own default of 1, called alongside `withDerivedRuntime()` at every one of those call sites. GitHub issue #156 then asked for the obvious follow-up: a `NoEAN-...` item's own EAN was never a real, scannable code, so `MediaItemDetailDialog`'s "refresh metadata" action can only ever come back `no_match` for one — wasting a real request (real per-call cost, for the LLM providers) per enabled provider for nothing every time it's used. `MediaItemService::isNoEanPlaceholder()` (checking against the same `NO_EAN_PREFIX` constant `generateNoEanPlaceholder()` itself is built from, so the two can't drift apart) is checked in two places: client-side, to grey out the button before the request is even sent, and server-side in `MetadataController::refresh()`, which short-circuits to `no_match` before querying any provider — the actual backstop, since the frontend check alone wouldn't stop a direct API call or a stale page.
- **Export/import strips instance-local personal identifiers** (GitHub issue #148, a privacy-review finding) — `ExportImportService::exportLibraries()` never includes an item's `captured_by_user_id` (GitHub issue #74) in its output, the same treatment `id`/`library_id` already got for being meaningless on another instance, and `insertItems()` additionally strips it from whatever an imported file actually contains regardless of source — a raw user ID that happens to collide with a real account on the *importing* instance (most commonly ID 1, the seeded admin) would otherwise falsely attribute that account with having captured an item it never touched, visible in `/reports/user-activity`. `shares[].user_email`, by contrast, is a *deliberate* exception to this same principle — see `exportLibraries()`'s own docblock for why it's intentionally not gated behind `$includeUsers` the way `system_settings`/`users`/`metadata_plugins` are. A library's own `owner_email` (GitHub issue #152, triggered by the user asking whether any data was missing from backups entirely) follows that same `shares[].user_email` precedent — previously absent from the export altogether, silently reassigning every restored library to whoever performed the restore/import instead of its real original owner, a genuine loss for a full backup/restore whose whole point is reproducing the exact prior state. `createLibraryFromExport()`'s `resolveLibraryOwner()` resolves it by email against an existing/just-restored account, falling back to the importing user (not a hard failure) when there's no match — the same tolerance `restoreShares()` already shows for a stale share email. `is_sample_library` was found missing the same way in the same audit and fixed alongside it, though currently inconsequential since nothing else in the app reads that flag yet. GitHub issue #153 then explicitly asked for `captured_by_user_id` itself to still be preserved in a *real* backup specifically (not an ordinary export) — reconciled with #148's own reasoning the same way, as `captured_by_email`: present only when `exportLibraries()` is called with `includeUsers: true`. Two bugs surfaced in the first version of that fix, both reported by the user and both fixed the same day: eager-loading the `capturedBy` relation to read its `->email` leaked a second, redundant `captured_by` key (Eloquent auto-serializes any *loaded* relation unless it's hidden too, same as any attribute) that re-exposed the exact raw id `captured_by_email` exists to avoid — fixed by hiding `capturedBy` explicitly; and resolving `captured_by_email` back onto `captured_by_user_id` on import was originally additionally gated behind `$restoreSettings`, which meant a backup restore that didn't separately opt into "restore settings" (the common case for restoring items/shares without overwriting the current instance's own accounts) silently discarded a perfectly resolvable value — fixed by resolving it unconditionally instead, the same way `owner_email`/`shares[].user_email` themselves already are. `insertItems()`'s own docblock has the full reasoning for both. A raw `captured_by_user_id` a hand-crafted import file might still carry is never trusted regardless. GitHub issue #154, also reported by the user, found the same class of gap one level down: `created_at`/`updated_at` are deliberately absent from every model's `#[Fillable(...)]` list (so an *ordinary* capture/creation path can never be made to spoof either one — a media item's own `created_at` is shown as "Hinzugefügt" in the Recent Additions report), and `exportLibraries()` never included them either, so a restore/import always silently reset both to the current time for every entity it (re-)creates — not just media items, but libraries, users, library shares, saved searches, and metadata plugins alike, everywhere this class recreates a row from scratch. `ExportImportService::applyHistoricalTimestamps()` is the one shared fix for all of them: called explicitly, right after `create()`/`updateOrCreate()`, only from this class's own restore/import call sites — `forceFill()` bypasses mass assignment entirely (letting every *other* caller of e.g. `MediaItemService::create()` stay exactly as unable to spoof a timestamp as before), and `saveQuietly()` avoids firing model events for what is, semantically, still "the original creation" being reproduced, not a genuine update.

`App\Domain\Libraries\CurrencyConversionService` (GitHub issue #64: converts a newly captured item's price into the admin-configured default currency via a live Frankfurter.dev exchange rate) is the deliberate opposite of the two rules above — it's called explicitly from the two genuinely-new-capture controllers (`MediaItemController::store()`, `MetadataController::import()`), not from `MediaItemService::create()` itself, precisely *because* that method is also the backup/import restore path and must reproduce a backup's historical prices exactly rather than re-converting them against today's rate. A future new capture entry point needs to call it explicitly too; it won't happen automatically just by going through `MediaItemService::create()`.

### Three media types, one pattern each
Book/CD/DVD-Blu-ray are three separate tables (`MediaBook`/`MediaCd`/`MediaDvdBluray`) with a fixed, non-overlapping attribute set per briefing chapter 6 — there's no generic "extra field" mechanism by design. A `Library.media_type` is immutable after creation (no update path exists for it anywhere in `LibraryController`). Code that needs to be type-generic (capture, export/import, stats) resolves the right model via `MediaItemService::modelClassFor()` rather than branching on `media_type` ad hoc.

### Metadata plugins are a real interface, not a config flag
`App\Domain\Metadata\Contracts\MetadataProviderInterface` + `MetadataProviderRegistry` (briefing 8.1) is the extension point for new metadata sources — implement the interface under `app/Domain/Metadata/Providers/<MediaType>/`, list the class in `MetadataProviderRegistry::defaultProviders()`, and it becomes toggleable via `metadata_plugins` (admin API) automatically. Books have eight implemented providers (OpenLibrary, Google Books — GitHub issue #20, Hardcover — GitHub issue #18, Amazon — GitHub issue #50, Claude — GitHub issue #59, OpenAI — GitHub issue #65, Gemini — GitHub issue #66, JPC — GitHub issue #131); CD has seven (MusicBrainz, Discogs — GitHub issue #22, Amazon, Claude, OpenAI, Gemini, JPC — GitHub issue #130); DVD/Blu-ray has six (UPCMDB, Amazon, Claude, OpenAI, Gemini, JPC). JPC's book provider (#131) was added after #130's original cd/dvd_bluray-only scoping turned out to be based on a wrong assumption — JPC does sell books — a cautionary example of not trusting an unverified scoping guess over what the user actually knows about a real-world retailer. A fourth scraping provider, Thalia, was implemented (GitHub issue #129) and later removed again (GitHub issue #134) once confirmed permanently non-functional against thalia.de's Cloudflare bot-management — see the `DEFAULT_DISABLED_PROVIDER_KEYS` docblock in `MetadataProviderRegistry` for the full story; it's mentioned here so a future search for "Thalia" in git history isn't mistaken for a still-existing provider. The rest of briefing 8.2's list are `TODO`s in the registry, not missing files to hunt for. The Amazon, Claude, OpenAI, and Gemini providers are all Beta and disabled by default — see "Known-incomplete areas" below. JPC started out the same way but was promoted out of Beta and enabled by default by GitHub issue #145, an explicit user decision after the string of real-world fixes (#133, #135, #136, #138, #140, #143, #144) made it reliable enough for everyday use. `MetadataImportService` only ever calls a provider that has a corresponding, *enabled* `metadata_plugins` row (`MetadataProviderRegistry::enabledProvidersFor()`) — listing a class in `defaultProviders()` alone doesn't activate it. `DatabaseSeeder` calls `syncToDatabase()` (`firstOrCreate`-based, so it's safe to run on every boot) specifically so a fresh install has all default providers enabled from the start; this was in fact missing until GitHub issue #17's investigation surfaced it — before that fix, a truly fresh install had zero enabled providers and every capture/search silently returned "no_match" no matter what was implemented.

A provider with admin-configurable settings (an API key, e.g. `UpcMdbProvider`) also declares `configFields()` (GitHub issue #29) — an array of `MetadataProviderConfigField`s (key/type/required) describing what `metadata_plugins.config` should contain. This is what lets `PluginsPage.tsx` render a real per-plugin settings form instead of a raw JSON textarea, without the frontend needing to know each provider's config shape ahead of time; a provider needing no configuration just returns `[]`. Field labels are deliberately not part of this — like every other backend-defined enum handed to the frontend (e.g. `Library.media_type`), only the stable `key` crosses the API, resolved to a translated label client-side via `admin.pluginConfig.fields.<key>` (falling back to a humanized version of the key for an as-yet-untranslated provider). `metadata_plugins` (including stored config/API keys) rides along on the same `includeUsers`/`restoreSettings` opt-in as user accounts in `ExportImportService` — it's exactly as sensitive as a password hash, so an ordinary library export never includes it, only a real backup does.

### Every MedInv-created table is prefixed `MEDINV_`
Set once via `MEDINV_DB_PREFIX` in `config/database.php` (applied to all four connections: sqlite/mysql/mariadb/pgsql) so the app can share a DB server without collisions (briefing 5.). This is why raw SQL/`DB::table()` calls must not hardcode table names — use Eloquent models or `$this->getTable()`, which already account for the prefix.

### All environment variables are `MEDINV_`-prefixed, including the database ones — with one deliberate exception
Laravel's stock `DB_*` config keys (`DB_CONNECTION`, `DB_HOST`, `DB_PORT`, `DB_DATABASE`, `DB_USERNAME`, `DB_PASSWORD`, `DB_PREFIX`, and the rest) are renamed to `MEDINV_DB_*` throughout `backend/config/database.php` (and the `database`-driver options in `config/cache.php`/`config/queue.php`, which fall back to the same connection) — a deliberate deviation from Laravel's defaults so that *every* variable this project reads from the environment consistently starts with `MEDINV_`, matching the vars from briefing chapter 16. When adding a new Laravel config option that reads `env('DB_...')` by default (e.g. from a fresh `composer require`), rename it the same way rather than leaving a stray unprefixed `DB_*` var. The one intentional exception is plain `TZ` (`SystemSetting::defaultTimezone()`), the near-universal, unprefixed Docker convention for a container's timezone (the same variable Sonarr/Radarr/Immich and most other self-hosted images honor) — treated as a cross-application OS-level standard rather than a MedInv-specific setting, precisely so deployers who already set `TZ` out of habit get the behavior they expect without having to also learn a MedInv-specific variable name. PHP does *not* read `TZ` on its own for `date_default_timezone_get()` (confirmed live — the old automatic fallback no longer exists in modern PHP), and the shipped Alpine image ships no `tzdata` package (no `/etc/localtime`/`/etc/timezone` either), so without this explicit `env('TZ')` read, a deployer's `TZ` setting was silently ignored entirely.

### Environment variables vs. runtime settings — don't confuse the two
Only the handful in briefing chapter 16 (`MEDINV_ADMINUSER`, `MEDINV_ADMINPASS`, `MEDINV_LOGLEVEL`, `MEDINV_TRUSTEDIP`, `MEDINV_RESTOREBACKUP`) plus the database/deployment ones above (`MEDINV_DB_*`, `MEDINV_URL`, `MEDINV_PortWeb`) are env vars, read directly via `env()` (seeder, `BruteForceProtection`, `docker/entrypoint.sh`). Everything else admin-configurable — mail/SMTP, backup interval & retention, brute-force thresholds — lives in the `system_settings` key-value table (`App\Models\SystemSetting::get()/set()`, `AdminSettingsController`) and is meant to be changed at runtime without a restart. `App\Providers\AppServiceProvider::boot()` copies the `mail.*` settings into Laravel's live mail config on every request specifically so `Mail`/`Password::sendResetLink()` pick up the admin-configured SMTP server instead of `.env`'s. The `timezone` runtime setting is a partial exception: once an admin explicitly saves one via `AdminSettingsController::updateTimezone()`, that stored value always wins, but *before* that, its default falls back to the unprefixed `TZ` env var rather than a hardcoded `'UTC'` — see `SystemSetting::defaultTimezone()`'s docblock and the "one deliberate exception" note above.

### API errors carry a machine-readable `error_code`, not just prose
`AuthController::loginError()` returns `{error_code, message}` instead of throwing `ValidationException` — the frontend maps `error_code` to a translated string via `errors.*` i18n keys (`LoginPage.tsx`), rather than pattern-matching on the English `message` text, which would break under a locale change or if the message wording changes. Follow this pattern for any other user-facing API error: add an `error_code`, not just a message, and a matching `errors.<code>` key in both `frontend/src/i18n/locales/{de,en}.json`. Also route it through `Controller::logApiError($request, $errorCode, $message)` (base `App\Http\Controllers\Controller`) so it lands in `storage/logs/laravel.log` with the requesting client's IP alongside the code and message — used today across six controllers (e.g. `AuthController::loginError()`, `UserController::protectedAccountResponse()`, `AdminSettingsController::testMail()`'s failure path), not an exhaustive list — grep for `logApiError(` rather than assuming this paragraph is current.

`errors.generic` is `LoginPage.tsx`'s *own* fallback specifically for an actual failed login attempt with no more specific `error_code` — its wording ("Login failed...") is accurate there and nowhere else. GitHub issue #156 (a follow-up question after #155) found every other unhandled-API-error fallback in the app (`CreateMediaItemDialog.tsx`/`MediaItemDetailDialog.tsx`'s own `describeApiError()`, `adminErrors.ts`'s `describeError()`/`describeBlobError()`, shared across every `admin/*.tsx` page) had been reusing that exact same key/text — so a real 500 while saving a media item read, confusingly, as if the *login* had somehow failed (this is in fact what made #155's own bug report read as an auth issue at first). `errors.actionFailed` is the separate, context-neutral key for all of those; new unhandled-error fallbacks outside LoginPage.tsx should use it, not `errors.generic`.

### Backups live under `storage/app/private/backups`, not `storage/app/backups`
Laravel 11+'s default `local` filesystem disk root is `storage/app/private` (`backend/config/filesystems.php`), not `storage/app` — `BackupService` uses `Storage::disk('local')`, so that's where `.zip` files actually land. Easy to get wrong when adding new storage paths; check `config/filesystems.php` rather than assuming the pre-11 default.

### The DB is update-ready: migrations run automatically, with a safety net
`docker/entrypoint.sh` runs `php artisan migrate --force` on every container start, so a new image with new migration files applies its schema changes with no manual step. Immediately before that, it runs `php artisan medinv:pre-update-backup` (`app/Console/Commands/PreUpdateBackupCommand.php`), which creates a backup via `BackupService` — but only when there are pending migrations *and* the database was already initialized (i.e. this is a real update, not first install or an unchanged restart) — so an update has a restore point without backing up on every ordinary restart. This guarantee depends on `backend/database/` (which holds `migrations/`/`seeders/`/`factories/` — application code, refreshed by every image build) never being covered by a persisted volume itself — only the actual sqlite data file is persisted, at `storage/database/database.sqlite` (nested inside the `storage` volume, not a sibling of the code directories), see the next section and GitHub issue #25 for why this used to be broken.

### The sqlite database file lives under `storage/`, not `backend/database/`
`config/database.php`'s sqlite connection defaults to `database_path('database.sqlite')` (`backend/database/database.sqlite`) for local, non-Docker dev — unchanged, and what the README's `touch database/database.sqlite` step still refers to. Docker deployments are different: `docker/entrypoint.sh` ignores any inherited `MEDINV_DB_DATABASE` for the sqlite case and is authoritative about the path instead, always `storage/database/database.sqlite` — `docker-compose.yml`'s `sqlite-data` named volume mounts onto that nested path (inside the already-persisted `storage` volume) rather than to `backend/database/` directly. Two bugs used to live here (issue #25): `docker-compose.yml` set `MEDINV_DB_DATABASE=medinv` by default — a value only meaningful as a *database name* for mysql/mariadb/postgres — which the sqlite driver silently took as a bogus relative file path, creating the database entirely outside any mounted volume (lost on every container recreation); and even without that, the old fallback path put the database file inside `backend/database/`, the exact directory `sqlite-data` was mounted onto — permanently freezing `migrations/`/`seeders/`/`factories/` at whatever they were when that volume was first created, so no later image update's changes to any of them ever took effect. The `sqlite-data` volume name is deliberately unchanged (only its mount point moved) so an existing deployment's real data keeps working automatically — Compose matches volumes by name, and renaming the key would make Compose treat it as new and empty. `entrypoint.sh` additionally has a defensive one-time move for anyone running the image directly (not via this docker-compose.yml) who had mounted their own volume at the old path.

### Backup restore has two trigger paths, one shared implementation
`BackupService::restore()` (briefing 9.3) reads a backup zip's `manifest.json` back out and hands it to `ExportImportService::importLibraries()` — the same conflict-resolution logic (rename/merge/overwrite/skip/cancel) instance-to-instance import already uses (briefing 9.1), so restore isn't a separate code path. The two triggers differ only in who picks the per-library resolution: `BackupController::restore()` takes `conflict_resolutions`/`restore_settings` from the admin UI request interactively, while `Console\Commands\RestoreBackupOnBoot` (`php artisan medinv:restore-backup <filename>`, run from `docker/entrypoint.sh` whenever `MEDINV_RESTOREBACKUP` is set) has no admin to ask and instead overwrites every conflicting library unconditionally via `importLibraries()`'s `__default__` conflict-resolution sentinel, plus always restores settings and user accounts — `MEDINV_RESTOREBACKUP`'s whole purpose is bringing the instance to exactly the backed-up state, e.g. resetting a demo/staging deployment on every restart.

### Automatic backups need both a Laravel schedule entry and something to actually invoke it
`backup.interval_mode`/`backup.cron_expression` (briefing 9.2, admin-configurable via `AdminSettingsController::updateBackup()`) are resolved into an actual cron expression by `BackupService::scheduledBackupCronExpression()`, registered in `routes/console.php` — but that alone isn't enough, since this image has no system cron daemon. `docker/supervisord.conf` runs a third process (`[program:scheduler]`) alongside nginx/php-fpm, a plain shell loop calling `php artisan schedule:run` every 60 seconds — Laravel's own scheduler resolution. The task itself is registered as `->everyMinute()`, not a dynamic `->cron($expression)`: `routes/console.php` loads on *every* console bootstrap (any artisan command, not just `schedule:run`), so evaluating `SystemSetting::get()` at registration time broke `php artisan migrate --force` itself on a brand-new database (no `system_settings` table yet) — the actual due-check happens inside the scheduled closure instead, via `Cron\CronExpression::isDue(Carbon::now())` (the explicit `Carbon::now()` matters too — `isDue()`'s own `'now'` default builds a plain `DateTime`, which ignores `Carbon::setTestNow()` and made this untestable otherwise).

### Fuzzy search is backend-specific, with a portable fallback everywhere else
`SearchService`'s `fuzzy` flag (briefing 13.) resolves differently depending on the active `MEDINV_DB_CONNECTION`, since there's no single privilege-free, index-usable typo-tolerant primitive across sqlite/mariadb/pgsql. On Postgres with the `pg_trgm` extension actually installed, it uses `word_similarity`'s indexable `%>` operator against a GIN trigram index built on `LOWER(column)` (a migration, `database/migrations/*_add_pg_trgm_indexes_for_media_search.php`, iterates `SearchService::SEARCHABLE_COLUMNS` — the single source of truth for searchable columns — to create these; deliberately `word_similarity`/`%>`, not plain `similarity()`/`%`, since the latter scores against a compared string's *entire* length and badly under-scores a short query cleanly matching inside a long field like `description`). Everywhere else (sqlite, mariadb/mysql, or a pgsql connection where `CREATE EXTENSION pg_trgm` failed — self-hosted Postgres instances don't always grant that privilege, and the migration is deliberately non-fatal if it does) falls back to `FuzzyTextMatcher`, a pure PHP word-level Levenshtein matcher: since a typo'd query word has by definition no substring overlap with the correctly-spelled field value, there's no SQL-level `LIKE` pre-filter that could narrow the candidate set without risking excluding the very row that should match, so this path loads every row in the visible libraries (still scoped through `LibraryAccessService`) and matches in PHP — an accepted trade-off given this app's realistic data volumes. `SearchService::pgTrgmAvailable()` checks (cached via the `database` cache store, not an in-process property — `SearchService` isn't a singleton, so per-request state buys nothing) whether the extension actually ended up installed, so a privilege-restricted Postgres deployment gets the same behavior as sqlite/mariadb rather than an error.

All three are marked `version()` `"v0.1-beta"` (GitHub issue #44 — no redundant "(Beta)" text in `name()` too), and — like the Claude/OpenAI/Gemini providers elsewhere in this list (JPC used to be a fourth example here too, until GitHub issue #145 promoted it out of Beta/opt-in) — `MetadataProviderRegistry::syncToDatabase()` leaves them disabled until an admin explicitly opts in (`DEFAULT_DISABLED_PROVIDER_KEYS`). For a long time never live-verified against the real site at all (doing so purely to develop/test it would itself be exactly the scraping traffic the feature's risk profile is about) — built and tested only against hand-built HTML fixtures modeled on Amazon's historically documented markup. GitHub issue #137 made a single, deliberate one-time exception to that stance (one real product-page fetch, at the requesting user's own explicit direction) and found real drift: the buy-box price now loads client-side (the static HTML's `#corePrice_feature_div` is genuinely empty), reachable instead via a hidden JSON blob that also disproved the standing "hardcoded amazon.com always means USD" assumption (a real page checked showed `EUR`); a book-specific `#bookDescription_feature_div` container the code didn't know about, leaving `description` silently always null for books; and a real trailing "Format: {value}" segment bleeding into `#bylineInfo` with no separating punctuation. See `AmazonScraping::amazonPriceAndCurrency()`'s own docblock for the fix and the explicit "not to be re-checked without the same one-time authorization" caveat that exception carries — the rest of this trait's fields remain unconfirmed against live markup. GitHub issue #139 is a real example of that caveat being honored rather than assumed away: a user-reported "Format: DVD" contaminating `cast` prompted asking for, and being granted, a second one-time exception — but both attempted re-checks (the search page, then a specific product page) were blocked by Amazon's bot detection this time, unlike #137's own successful check. Rather than guessing at a confirmed shape that couldn't actually be confirmed, the fix (`stripAmazonFormatContamination()`, widened from #137's suffix-only match to anywhere in the string) is explicitly documented as unverified hardening, not a confirmed fix. `AmazonDvdBlurayProvider`'s `genre`/`subtitles` fields (GitHub issue #140, which added both columns to `MediaDvdBluray`) are best-effort `amazonBullet()` label guesses ("Genre"/"Genres", "Subtitles") — neither was ever seen on a real Amazon page — GitHub issue #141 tried again, explicitly authorized, against three different real DVD/Blu-ray pages, and all three were blocked (two HTTP 500s, one 503), the same outcome #139 already had — so unlike most of this trait's other fields, treat these two as unconfirmed even by this provider's own already-cautious standard. `cast` itself was removed entirely by GitHub issue #150 — a further user report that it was wrong in general, combined with #141's live re-check being blocked before the underlying "Actors" bullet label could even be inspected, left no way to actually fix it with any confidence, so it was dropped rather than guessed at further, the same "no confirmed label, don't set the field" stance `JpcDvdBlurayProvider` already takes for this exact field.
- Thalia (all three media types) was implemented as a second scraping-based provider family (GitHub issue #129, `App\Domain\Metadata\Providers\Thalia\ThaliaScraping` + `Thalia{Book,Cd,DvdBluray}Provider`) and later **removed again** (GitHub issue #134): diagnosing why a user's real deployment returned zero results (GitHub issue #132) surfaced that thalia.de runs Cloudflare bot-management with an active JS challenge (`cf-mitigated: challenge`, confirmed via a plain `curl` request with a spoofed desktop User-Agent) — a fundamentally different, and deliberately not-attempted-to-defeat, category of defense than Amazon's/JPC's own weaker bot detection (same no-evasion restraint `AmazonScraping`'s own docblock already commits to). Since this made the provider not merely unreliable but confirmed permanently non-functional, it was removed rather than left as a dead, still-toggleable option in the plugin list; see `MetadataProviderRegistry`'s `DEFAULT_DISABLED_PROVIDER_KEYS` docblock and `database/migrations/2026_08_20_193000_remove_thalia_metadata_plugins.php` (which also cleans up any pre-existing `metadata_plugins` rows on an install that had already seeded them) for the full story.
- JPC (all three media types — GitHub issue #130 for cd/dvd_bluray, extended to books by GitHub issue #131 once it turned out JPC does sell books, contrary to #130's own original assumption) is a scraping-based provider family (`App\Domain\Metadata\Providers\Jpc\JpcScraping` + `Jpc{Book,Cd,DvdBluray}Provider`), promoted out of Beta/opt-in and enabled by default by GitHub issue #145 (unlike Amazon, which remains Beta) after the fixes below made it reliable enough for everyday use. Unlike thalia.de, jpc.de did *not* block a direct, one-time, read-only fetch during pre-implementation research, which confirmed meaningfully more here: the `/jpcng/{category}/detail/-/art/{slug}/hnum/{id}` product-URL shape, a consistent `<title>`-tag format ending `({Format}) – jpc.de` but with two *different, conflicting* byline conventions depending on media type (`{Artist}: {Titel}` for a CD, byline first, colon-separated; `{Titel} - {Autor}` for a book, byline last, hyphen-separated — `JpcScraping::parseJpcTitleTag()`'s `$splitTitleOnDash` parameter is opt-in per caller specifically so a film title's own legitimate " - " subtitle never gets misread as a byline), a full set of real German detail-row labels (`Regie:`, `Sprache:`, `Spieldauer ca.:`, `UPC/EAN:`/`ISBN-13:`, `Erscheinungstermin:`, `Verlag:`, `Einband:`, `Umfang:`, ...), and — uniquely among this app's scraping providers — a cover-image URL directly derivable from the EAN/ISBN-13 (`https://media1.jpc.de/image/w2400/front/0/{code}.jpg`), no `<img>`/`og:image` extraction needed at all. The search endpoint itself wasn't found during #130's own research — several direct guesses were tried and ruled out with a concrete 404/503, but no working one was found. That gap turned out to be a real production bug (GitHub issue #133 — every search/lookup silently returned no results, since the originally-guessed `/jpcng/search` path never actually existed): fixed once the reporting user shared the real `<input name="fastsearch" ...>` element from jpc.de's own header search box, letting `JpcScraping::SEARCH_PATH`/`SEARCH_QUERY_PARAM` be confirmed live as `/jpcng/home/search`/`fastsearch` — see `SEARCH_PATH`'s own docblock for the full verification (including why every previously-tried parameter name failed silently rather than erroring, which is what made this particular gap so easy to miss by trial and error alone). GitHub issue #139 also traced a user-reported "Format: DVD" landing in `cast` back to the *Amazon* provider, not JPC — `JpcScraping` was already confirmed to have no "Darsteller"-style cast label at all (see below) and was cleared during that investigation. GitHub issue #140 (which added `genre`/`subtitles` columns to `MediaDvdBluray`) confirmed both `Genre:`/`Untertitel:` as real jpc.de detail-row labels — `genre` was in fact already being extracted by `jpcProductPage()` (used for books, the only model with a `genre` column until then) but never mapped into `JpcDvdBlurayProvider`'s own candidate; `subtitles` needed the extraction added too. That same issue also confirmed jpc.de's DVD/Blu-ray pages carry no film-synopsis container at all (checked across 3 real pages, several plausible class/id/label patterns each came up empty) — so, unlike JPC's own `description` field for books, there's no possible source for one here; `description` stays unset for this provider's DVD/Blu-ray candidates. GitHub issue #143 found that a Genre <dd> can carry more than just the genre itself — confirmed live on "Fringe Season 5" (EAN 5051890205261, a 5-DVD TV-season box set), whose Genre row reads "Thriller, (13 Episoden)" rather than just "Thriller", the episode count sharing the same element with no separate label of its own — `stripJpcGenreAnnotation()` strips a trailing parenthetical annotation containing a digit, confirmed only for this one live case. A related check across other media types (GitHub issue #144) found no confirmed contamination in book fields (Verlag/Einband/Sprache/Umfang all clean across five real book pages checked) but did find a "Genre:" detail row is never present on any real book page checked either — genre extraction stays wired up for JpcBookProvider (a genre-tagged book category not yet sampled cannot be ruled out) but is expected to return null in practice, not a regression. The same check also found a CD track title issue: two real CD pages (a plain single album and a vinyl box set) both showed a track title with a trailing "Hörprobe Track {n}: ..." (audio-preview control) annotation repeated after it — unlike #143, this could not be confirmed with a byte-exact fetch (no working direct network path to jpc.de in that check's sandbox), so `stripJpcTrackPreviewAnnotation()` strips it defensively, the same unconfirmed-but-consistent-pattern treatment #139 gave Amazon's cast contamination. A separate, unrelated security-review finding (GitHub issue #146) hardened `absoluteJpcUrl()` to only follow an absolute href that stays on jpc.de itself — that URL is fetched server-side by `jpcProductPage()`, so an unrestricted absolute href out of jpc.de's own search-results markup would have been a server-side-request-forgery primitive, unlike AmazonScraping, which never trusts a scraped href as a fetch target at all (it reconstructs the product URL itself from a `data-asin` attribute against the fixed amazon.com host).

  A second, more fundamental production bug (GitHub issue #135 — "very few attributes, missing cover") turned out to trace back to the research tool used for #130/#131's original implementation: it converts a page to Markdown before answering questions about it, and had silently misrepresented DOM structure it was asked to quote "verbatim" — real jpc.de markup mixes bare `<dt>Verlag:</dt>` with label text wrapped in an inline tag (`<dt><b>UPC/EAN:</b></dt>`) on the very same page, and `jpcDetailValue()`'s original sibling-walk matched on that inner `<b>` rather than the enclosing `<dt>`, so it silently found no value for almost every wrapped label — including the one behind EAN extraction, which is also what the cover-URL derivation depends on. Fixed (GitHub issue #135) by matching specifically on `<dt>`/`<th>` elements using their full descendant-inclusive text rather than an arbitrary element's own direct text node — see `jpcDetailValue()`'s own docblock. That same re-verification — this time against byte-exact HTML fetched directly with `curl`, not through the Markdown-converting research tool — also found that jpc.de embeds real schema.org **Microdata** (`itemprop`/`itemscope`), reversing two of #130's own original decisions: `price`/`currency` are now extracted (a confirmed `schema.org/Offer` block), and CD track listings are now extracted too (`schema.org/MusicRecording` items, title only, no duration) — `cast` on the DVD/Blu-ray provider remains unset (still no confirmed label/microdata for it) and `description` remains unextracted for all three media types (the one real source found, a `<meta name="description">` tag, turned out to be generic marketing boilerplate, not a real synopsis) — see `JpcScraping`'s own docblock for the full, itemized confirmed-vs-guessed breakdown.

  A third bug (GitHub issue #136 — "Anzahl der Discs" stuck at 1 despite `medium` correctly showing e.g. "2 DVDs"): jpc.de has no dedicated disc-count label at all — confirmed live on a real multi-disc release — the count lives only inside the same title-tag-derived format string `medium` originally came from unmodified, which `disc_count` (a `MediaCd`/`MediaDvdBluray` column with its own DB-level default of `1`, silently masking the gap) was never derived from. Fixed by reusing the same `parseLeadingInt()` every other leading-number field in this trait already uses, against that format string. A follow-up (GitHub issue #138) then removed the resulting redundancy that fix itself introduced — `medium` no longer repeats the same count `disc_count` now carries as its own field ("2 DVDs" → "DVD", "2 LPs" → "LP") — see `JpcScraping::stripJpcDiscCount()`'s own docblock.
- LLM-backed metadata providers (Claude, GitHub issue #59; OpenAI, GitHub issue #65; and Gemini, GitHub issue #66 — all three across all three media types) are a fourth provider category alongside the plain-API and scraping ones above — `App\Domain\Metadata\Providers\Claude\ClaudeMetadataProvider` / `App\Domain\Metadata\Providers\OpenAi\OpenAiMetadataProvider` / `App\Domain\Metadata\Providers\Gemini\GeminiMetadataProvider` (each a shared trait) + `{Claude,OpenAi,Gemini}{Book,Cd,DvdBluray}Provider` call the Anthropic Messages API / OpenAI Responses API / Google Generative Language `generateContent` API directly (raw `Http::`, matching every other provider's zero-SDK convention) with structured outputs and a server-side web-search tool declared on every request, so the model grounds its answer in a real page instead of answering from training knowledge alone. The three vendors' request/response shapes differ in several concrete ways beyond just the endpoint/model (see `OpenAiMetadataProvider`'s and `GeminiMetadataProvider`'s own docblocks for the itemized lists, each verified against that vendor's current API reference before implementing rather than from training knowledge, per the same caution #59's own docblock already documents for Claude) — notably, OpenAI's structured-output schema lives under `text.format` (with a required schema `name`, which neither Claude nor Gemini has an equivalent for) rather than `output_config.format`/`generationConfig.responseSchema`, its `input` array carries the system-role turn inline rather than a separate top-level `system` string/`systemInstruction` object; Gemini's `responseSchema` is a subset of the OpenAPI 3.0 Schema Object rather than plain JSON Schema, so nullability is a sibling `nullable: true` boolean instead of Claude/OpenAI's `type: [T, "null"]` union, and its web-search tool (`{"googleSearch": {}}`) needs an explicit PHP `(object) []` rather than `[]` to json_encode as `{}` instead of `[]`; a declined request surfaces as a `"refusal"`-type content item for OpenAI, a top-level `stop_reason` flag for Claude, and a prompt-level `promptFeedback.blockReason` (with no `candidates` array at all) for Gemini. The admin-configurable `prompt` setting is a `'textarea'`-type `MetadataProviderConfigField` (GitHub issue #59's addendum, the first use of that field type) pre-filled with a default naming real retailers/databases (JPC, Thalia, Amazon, Discogs, IMDb, WorldCat) to check — identical wording across all three vendors, since the instruction itself isn't model-specific. `price`/`currency` are deliberately never requested (an even worse hallucination risk than an exact ISBN) and `coverUrls` is always `[]` (a plain chat completion can't return a genuine existing image URL). `sourceType()` returns `'llm'`, a third value alongside `'api'`/`'scraping'` (GitHub issue #55) — like Amazon above, `version()` is `"v0.1-beta"` and all nine providers (three each for Claude, OpenAI, Gemini) are disabled by default; unlike Amazon, none of them was ever live-verified against the real Anthropic/OpenAI/Google API (all three network-reachable from this sandbox but no usable credentials — see each trait's own docblock). All three `{Claude,OpenAi,Gemini}DvdBlurayProvider::ITEM_FIELDS` gained `genre`/`subtitles` (GitHub issue #140, identical shape/pattern to `cast`) once `MediaDvdBluray` got both columns — an ordinary schema addition, not a new confirmed/unconfirmed distinction, since a grounded LLM answer isn't scraped markup with a specific label to (dis)confirm.
